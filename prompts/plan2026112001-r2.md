# 修改思路：正向 WebSocket 客户端也支持 Token

## 用户意见
用户补充要求：“client也要增加token 支持”。据此扩展现有 Token 认证范围：除 `loop_server` 验证反向连接外，`loop_client` 也应能在连接上游时发送同一 Bearer token 头。

## 当前状态核对
当前工作区已存在服务端入站认证实现：`BotServerBuilder::access_token` 配置 token，`loop_server` 握手校验 `Authorization: Bearer`；设计文档仍注明不含客户端出站 token。因此本轮拟补足客户端出站认证，不重复实现服务端部分。

## 拟实施方案
1. 在 `BotContextBuilder` 增加可选 `access_token(...)` 配置，并将其安全地传入 `BotContext`，未配置时保持现有连接行为。
2. 在 `loop_client` 的每次连接/重连尝试中，以当前 URL 构造 WebSocket Upgrade HTTP Request；若配置了 token，则设置 `Authorization: Bearer <token>`，再调用 tokio-tungstenite 的请求形式 `connect_async`。不得把 token 拼进 URL/query。
3. 校验配置的 token 非空；确保 token 不出现在 Debug 输出、连接日志、错误上下文或示例硬编码内容中。握手失败继续走既有重连等待机制。
4. 更新 `runbot/examples/client.rs` 以环境变量可选读取 token；更新根 README 的正向 WS 接入示例，说明上游服务端需配置相同 access token、默认无 token 仍兼容，以及明文 `ws://` 下凭据会泄露，应在生产使用 TLS/WSS 或可信 TLS 代理。
5. 更新 `doc/websocket-token-auth.md`，把客户端出站发送与服务端入站验证作为同一认证方案的两个方向，并补充 API、流程、安全边界、验收标准和兼容性说明。
6. 完成后检查格式与编译，运行与改动相关的 workspace 检查/测试；记录已知既有失败及其基线状态。

## 兼容性与风险
- 未配置 token 时不增加请求头，兼容现有连接。
- 配置 token 后，只有接受相同 Bearer token 的上游可完成握手，这是启用该选项后的预期行为。
- `BotContextBuilder` 当前是公开结构体且字段公开。新增 builder 状态字段可能影响直接使用 struct literal 的下游代码；主流 `BotContextBuilder::new()` 链式用法不受影响。实施时应评估是否通过新配置包装类型避免该源码兼容影响；若无低复杂度兼容方案，则在文档中明确记录并沿用现有 builder API。
- 使用标准 Authorization header，不将凭据置于 URL，避免 URL 日志/代理记录扩散。
