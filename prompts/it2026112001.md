## 发现与说明

1. **客户端错误日志泄漏风险已修复**：原先 `loop_client` 使用 `Debug` 记录 `WsError::Http`，上游若反射 Authorization，响应头会随 Debug 进入日志。本轮改为 `Display`（仅输出 HTTP 状态），并由 S-02 的反射响应用例验证。
2. **第三方 TRACE 日志风险**：tokio-tungstenite/tungstenite 的客户端握手 TRACE 会打印原始 HTTP 请求，其中包含 Authorization。runbot 自身日志已使用不含凭据的输出，且本轮日志测试采集 INFO 及以上；生产环境不应开启第三方 handshake TRACE，或应通过过滤器屏蔽。
3. **重复 Authorization 语义未定**：X-01 记录当前“取第一个值”的行为，不应直接视为长期安全契约。
4. **空白/非 ASCII Token 契约未定**：X-02 仅记录实际行为，不建议在未确认前增加新的 build 阶段拒绝规则。
5. **服务端 bind 失败处理**：为支持端口竞争重试，`loop_server` 从 `unwrap` 改为返回 `Error::StateError`，不改变成功路径。
6. **示例 R-01 未进程级启动**：只做了源码核对，未把示例二进制作为独立进程联调。
7. **覆盖率未测量**：环境没有 `cargo-llvm-cov`，未填造覆盖率数值。

## 结论

认证相关新增代码和测试均通过；服务端拒绝隔离、完整 401 响应、客户端重连、凭据脱敏和真实 TCP 接入循环均有可复现证据。完整 workspace 回归的非零退出码仅来自基线已有的 `test_demo_command_ban` 失败，不是本轮认证改动引入。R-01 与 X-04 保留 Partial/Blocked 状态，未标记为通过。
